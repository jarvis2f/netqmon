# Collector CPU 排查与修复（2026-10-23）

## 生产证据

2026-10-22 23:51～23:55（北京时间），`pve-debian12-prod` 共 2 个 CPU 核。
`netqmon-controller:v1.1.0-beta.1` 中的 collector 高负载采样约占用 0.95 个核；
两段 12 秒 perf 采样中，DPI worker 占 collector 样本的 50%～67%。
热点包含 `RawTable<FlowKey, ActiveFlow>::clone`、字符串复制、分配和缺页处理。
同期 I/O wait 较低，没有持续 swap-in/out。

SQLite 约 2.9 万条会话的 `ended_at IS NULL`，其中约 2.89 万条超过 30 分钟无流量更新。
这些是数据库统计，不是直接读取 Rust map 的结果；源码会在启动时加载所有未结束会话。
未正确收到或关联 End 时，原实现不会超时回收它们。

## 第一轮变更

- SQLite 和 ClickHouse 上报持久化只暂存本批涉及的连接，成功后发布变更，保留失败重试语义。
- SQLite 的单条 late-DPI 回填改为按协议方向的三次哈希查找，不再复制、扫描整个 map。
- SQLite 按 Collector 收到上报的时间做 30 分钟兜底回收，每分钟维护时执行；
  启动时也清理过期恢复记录和遗留未结束会话，再加载缓存。
  生命周期 Idle 通知刷新接收时间，延迟或旧时间戳的数据不会被立即回收。
- 回收前保存累计计数，延迟 End 或同一 lifetime 后续数据可从持久化会话恢复。
  活跃计数直接来自缓存，包含尚未 checkpoint 的连接。
- 新增 SQLite migration 8，为 late-DPI 五元组查询和未结束 checkpoint 清理添加索引。
- 复用设备 ID 查询结果和热点 prepared statements；消除逐 flow 临时 TelemetryBatch 复制。
- 自托管端点去重由线性 Vec 查找改为 HashSet。
- 维护任务跳过错过的 tick，避免慢维护完成后立即连续补跑；回收先于聚合执行。

SQLite 是本次生产问题实际使用的后端。ClickHouse 本次只同步优化了上报缓存暂存，
其启动恢复、过期回收和 late-DPI 全扫描仍需单独处理。

## 其它性能问题

以下来自源码审查，尚未通过修复后的生产 profile 量化占比。

1. **已优化：SQLite 历史汇总。**持久化增量队列替代每分钟全历史扫描，见下方第二轮记录。
2. **已优化：全局锁覆盖慢操作。**分类移到状态锁外；文件数据库的分析查询和维护使用独立连接。
3. **已优化：实时快照复制、排序。**共享不可变快照，按变化维护连接顺序，减少逐批复制和排序。
4. **优先级中：rollup 仍逐 flow 写多个维度，自托管 evidence 仍逐 flow 解析 JSON。**
   本次已减少解析 SQL 和设备查询；后续可以批内按 rollup key 聚合写入，
   以及一次解析 evidence flags，减少高流量下的重复工作。
5. **需追踪：End 未正确结束旧会话的上游原因。**
   兜底回收限制后果，但尚未确认是 End 丢失、Agent 重启，还是 NAT/conntrack 归一化前后 tuple 变化。
   后续应关联原始 key、boot、policy_flow_id 与归一化 tuple 验证，避免只依赖 GC 掩盖问题。

## 第二轮优化

### 增量汇总

migration 9 为五个维度的 hour/day 增加持久化 pending 表。minute/hour 的 INSERT、UPDATE
触发器记录指标差额，维护事务只消费已完成时间桶的差额，提交后删除 pending 工作。
迟到数据可更新任意旧时间桶；retention 删除明细不会撤销已经保留的长期汇总。
late-DPI 即时修改已物化层时，会抵消对应 pending 差额，避免后台再次累计。
失败回滚和进程重启保留未完成工作；retention 同时清理超期 pending。

升级时会做一次历史对账，补齐尚未物化的正向差额，保留因源明细过期而较大的已有汇总。
该扫描发生在 schema 升级，不会在每分钟维护中重复。已有历史异常不会被这次迁移擅自向下修正。

### 锁与连接

- processing mutex 维护上报与 DPI 更新的顺序，保护 service-binding、DNS、favicon 缓存所有权。
- 全局 inner mutex 只用于取得本批数据库证据、提交结果和更新轻量状态；分类 IPC、设备识别和
  Geo 计算在状态锁外完成。出错时仍归还缓存。
- 文件数据库分析接口由独立 reader source 建立只读 WAL 事务。创建查询上下文本身也不需要
  ingestion mutex，避免写入正在等待数据库锁时连带阻塞查询入口。
- 维护使用独立写连接；SQLite 写事务仍由数据库串行化。活跃流 GC 保持在拥有缓存的 writer 上。
- 内存数据库保留原连接路径，确保测试及内存模式能看到同一份数据库。
- Geo provider 使用共享引用同步至查询元数据，活跃计数以原子快照提供，避免查询复制流缓存。

### 实时快照

完整快照和单条连接状态通过 Arc 共享。修改连接时只复制该条仍被旧快照引用的记录，
旧快照和 SSE 事件保持不可变。BTreeSet 维护显示顺序与容量淘汰；每批只更新涉及的排序项，
生成有序快照时不再全量排序。JSON 字段结构及 SSE 事件名保持一致，序列化仍发生在订阅端。

### 延长观察发现的并发写入补修

02:33～02:34 的每分钟维护期间再次出现偶发 `sample classification update failed:
database is locked`。late-DPI 使用默认 deferred transaction，先读取旧快照，再尝试
升级为写事务；另一个维护连接持有写事务时，SQLite 可以立即拒绝升级，绕过 busy timeout。

新增回归测试先由维护连接持有写锁，再执行真实的 DPI 回填。在 beta.3 实现上该测试失败；
将主写连接和独立维护连接的默认事务改为 IMMEDIATE 后通过。只读查询仍使用独立 WAL
deferred transaction。补修使写入在读取前取得写资格，避免读快照升级冲突。
本地 storage 55 项单元测试、1 项兼容性测试通过；Linux Collector、storage 与协议测试通过。
