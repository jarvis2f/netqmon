# NetQmon v1.1.0 发布说明

> 整理日期：2026-10-23。比较基线为 `v1.0.3`（`87763c7`），覆盖截至 `v1.1.0-beta.5`（`d0b78cb`）的 17 个提交，以及正式版准备中的组件版本展示和更新检查。GitHub Release 使用下方指定的四条文案；详细说明及维护者记录保留在本文供核对。

## GitHub Release 文案

1. **新增流量策略与 QoS**：按客户端、应用或分类执行阻断、放行、上传/下载限速，支持每周时段计划。
2. **优化 Collector 性能**：减少缓存复制与扫描，增加 SQLite 遗留连接回收、增量历史汇总，优化实时快照并修复 DPI 回填的并发锁竞争。
3. **改善应用识别与流量关联**：补充 TLS SNI 提取，改善双向采样证据合并、DNS 关联及 NAT 流向判断。
4. **改善客户端和移动端体验**：新增客户端批量命名，优化流量动画，减少后台订阅和不必要的重绘。

## 发布正文

NetQmon v1.1.0 新增流量策略管理，在网络监控与应用识别的基础上，支持针对设备和应用执行阻断、带宽限制及每周时段计划。同时优化 Collector 长时间运行时的资源消耗、历史统计与实时查询，并改进移动端浏览体验。

### 新增流量策略与带宽管理

- 新增独立的「流量策略」页面，支持创建、编辑、启停、删除与筛选策略。
- 按客户端 MAC 选择设备，并结合应用或应用分类匹配流量；支持设置应用识别最低置信度，减少识别证据不足时的误匹配。
- 支持客户端互联网访问阻断，以及指定客户端的应用/分类阻断和放行规则。放行仅影响 NetQmon 的相应阻断判决，不绕过外部防火墙和带宽限制。
- 支持分别设置上传和下载速率上限，包括每个客户端的总带宽限制，以及客户端内指定应用/分类的带宽限制。同一客户端、策略和方向下的应用连接共享额度，IPv4 与 IPv6 共享相应预算。
- 支持每周时间计划，可指定时区、星期和生效时段。
- 支持设置规则匹配优先级，数值越小优先级越高。

### 新增策略编辑、预览和执行状态追踪

- 提供可视化表单和高级 YAML 两种编辑方式，支持策略校验。
- 提供只读模拟预览，可输入客户端、应用、分类、置信度与时间，查看匹配规则和判决结果。
- 展示「期望 → 已发送 → 已确认 → 最近完整应用」四阶段状态，区分配置已保存、Agent 已接收和规则已实际应用。
- 展示设备能力、不支持或降级原因、部分应用及失败状态，方便排查策略未生效的问题。
- 新增策略变更记录，支持查看修改前后配置；检测并发编辑冲突并保留本地草稿。
- 展示 Agent 上报的限速队列流量和阻断计数，支持恢复策略数据库备份后的重新发布。

### 新增网关本地策略诊断与恢复

- 新增 `netqmon-agent policies status`，查看本地策略版本、执行能力及限速状态；支持 JSON 输出。
- 新增 `netqmon-agent policies unlock`，本地紧急停用策略并清理可验证归属的 NetQmon 规则与队列，同时阻止后续远程快照重新启用策略。
- 新增 `netqmon-agent policies resume`，取消紧急停用并恢复最后有效策略；含应用规则的快照由运行中的 Agent 在后续协调周期恢复。
- 自动探测物理链路容量，支持桥接/VLAN 路径解析及多千兆链路；探测失败时可显式配置接口容量。
- 执行前检查网络拓扑、flow offload、客户端身份、队列归属和数据包标记冲突，并报告能力限制。

### 优化 Collector 性能与稳定性

- 优化流量上报和延迟 DPI 识别回填，减少随活跃连接数量增长的缓存复制与扫描开销。
- SQLite 新增过期活跃连接回收和启动清理，限制长期运行时遗留连接的缓存增长，并保留迟到上报和结束事件的恢复处理。
- SQLite 历史统计改为增量汇总，减少定期维护对全量历史数据的重复扫描；支持迟到数据、分类修正、事务回滚和重启后继续处理。
- 缩小采集处理的全局锁范围，文件型 SQLite 的分析查询与维护使用独立连接，减少查询与写入互相等待。
- 优化实时连接快照的共享和排序，减少大量连接下的重复复制与排序。
- 修复 SQLite 维护与延迟 DPI 回填并发时，由读事务升级写事务引发的锁竞争。

### 改善应用识别与流量关联

- 从已有的有界 TCP 采样中补充提取 TLS ClientHello SNI，为 nDPI 未返回主机名的情况提供识别依据，无需解密流量。
- 改善 NAT 不同观测点的双向采样证据合并，避免另一方向缺少主机名时覆盖已有证据。
- 改善 DNS 解析结果与加密流量的域名关联；对同一连接中存在冲突的应用签名保留不确定状态，减少错误应用归属。
- 修正 conntrack 流向判断，使用完整连接元组匹配，减少 NAT/重定向场景下的方向误判。
- 改善应用阻断在短连接重建时的连续性，并按策略版本、有效期和调度边界约束端点阻断缓存。

### 改善客户端管理与移动端体验

- 新增客户端批量命名，可按行粘贴「MAC 地址 名称」，支持格式校验、重复检测和设备匹配检查。
- 批量保存显示进度；部分更新失败时保留失败项，方便重试。
- 优化流量拓扑粒子、连线和速率过渡，使实时流量变化更平滑。
- 在页面进入后台时暂停相关实时订阅和刷新，返回前台后恢复；不可见区域暂停持续动画，并适配减少动态效果偏好。
- 降低触屏设备的动画负担和不必要的界面重绘。
- 网关状态使用轻量查询和状态订阅，减少仅为显示在线状态而传输完整实时数据的开销。
- 系统状态区显示 Controller 与 Agent 版本，并检查 GitHub 发布记录，提供新版本发布说明入口；稳定版本忽略预发布版本，检查失败时明确显示状态。

### 改善 OpenWrt 安装与发布可靠性

- 补充流量策略所需的 OpenWrt 依赖和策略连接配置。
- 修复预发布 APK 附件下载地址与安装清单的文件名不一致问题。
- 修复可选架构的包构建流程，完善 RISC-V APK 打包及 MIPS 下载校验、静态链接和启动检查。
- 保持现有架构支持分级；RISC-V、MIPS 的构建修复不代表其自动提升为正式支持等级。

### 升级说明与能力边界

- 建议同时升级 Controller 与 Agent，以使用完整的策略管理、下发和执行能力。新策略协议通过独立 WebSocket 传输。
- 升级前备份 Controller 完整数据目录。本版本自动执行 SQLite 7～9 号迁移，并新增独立策略数据库；历史数据首次迁移会执行一次对账，启动耗时取决于数据规模。
- 策略数据库默认位于 `/data/netqmon-policies.db`，即使分析存储使用 ClickHouse 也需要持久化该文件；可通过 `NETQMON_COLLECTOR_POLICY_DB_PATH` 修改位置。
- 策略执行需要受支持的 Linux/OpenWrt 拓扑和内核能力；限速依赖 `tc-full`、HTB、fw classifier、fq_codel 等组件。应关闭可能绕过策略路径的软件/硬件 flow offload。
- 使用 Router 应用限速时，需要在 Agent 采集接口配置中包含 LAN 和 WAN。使用单臂拓扑时，应确保双向流量均经过 Agent，并关闭 ICMP 重定向。
- 实际能力以 Agent 上报结果为准，保存或确认收到策略不代表已完整生效。
- 当前客户端选择器为 MAC 地址；应用策略必须选择具体客户端，不提供全局应用共享带宽池。
- 当前单方向速率上限可配置为 64 Kbps～1 Gbps，上传和下载分别设置，留空的方向不限速；物理链路容量探测可支持更高链路速率。
- 跨午夜计划需拆为两个时间窗口。规则匹配优先级不代表队列优先转发能力。
- Agent 通过反向代理连接 Controller 时，应允许策略 WebSocket 升级；不可信网络使用 WSS。明文 `ws://` 默认仅允许回环、RFC 1918 或 ULA IP 主机。

### 性能表述依据

仓库中的 [Collector 性能排查与验证记录](collector-performance-review.md) 包含受控基准、Linux 测试和 beta.3/beta.4 生产验证。可据此表述为降低缓存处理、历史维护和实时快照开销。

如需引用数字，必须注明测试口径：例如同机 release 构建中，30,000 个无关缓存项下，100 次单流 DPI 回填从 3,089.14 ms 降至 2.93 ms；100,000 条历史分钟记录下，100 次无增量维护从 3,687.52 ms 降至 4.38 ms。基准对比起点是 `a6ab159`，并非直接对 `v1.0.3` 的生产测试。

生产 CPU 数据来自不同时间和不同流量条件，不应直接写成固定百分比性能提升。beta.4 稳态观察窗口内未出现锁错误，但启动阶段仍记录过一次 DPI 写锁超时，不应声称完全消除所有锁超时或采样丢弃。

SQLite 的过期缓存回收、启动清理及增量汇总优化不应泛化为 ClickHouse 已具备同等实现；ClickHouse 本次同步优化了上报缓存暂存。

### README 与实现的差异

现有中英文 README 部分描述超出当前实现，发布前宜同步修正：

- “MAC/IP/hostname 选择客户端”：当前策略校验只接受客户端 MAC。
- “网关全局聚合限速”：当前要求指定客户端，每个客户端独立预算；不支持全局应用共享带宽池。
- “Allow / Priority” 动作：实际动作只有 `block`、`allow`、`limit`，`priority` 是规则匹配排序字段。
- “零开销”“线速”“杜绝误配”“确保路由器永不挂起”等绝对表述缺少相应验证，不用于正式发布说明。
